# kb_qa · 项目深潜：领域 RAG 知识问答

> 本文件是项目一的技术深潜：架构细节、设计决策、评测口径、接口契约。
> 快速开始与总体指标见[根 README](../README.md)。

## 1. 解决的四个真实问题

| # | 问题 | 方案 |
|---|---|---|
| 1 | 文档格式与层级复杂，**固定切分导致语义断裂**，召回噪声大 | 递归切分 + 标题层级保留 + **父子块双层索引** |
| 2 | 纯向量检索对**专有名词、编号、型号**命中率低 | **BM25 + 向量双路召回**，RRF 融合；编号/型号走规则召回 |
| 3 | 长文档超出上下文窗口，**模型产生幻觉且答案无法追溯** | **低置信拒答** + Prompt 强制**引用原文片段** |
| 4 | 检索调参依赖人工，**缺少可量化、可回归的评测手段** | 自建评测集 + **逐层消融实验** + 分类型统计 + Badcase 回流 |

## 4. 接口

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/health` | 健康检查 + 索引规模 |
| POST | `/chat` | 一次性问答 `{"query": "..."}` |
| POST | `/chat/stream` | SSE 流式问答 |
| GET | `/chat/stream?q=` | SSE 流式（浏览器 `EventSource` 可直接联调） |
| GET | `/debug/retrieve?q=&top_k=` | **只检索不生成** —— 调检索参数最常用 |
| GET | `/debug/service` | 服务自描述（配置指纹） |

SSE 事件顺序（前端轨迹面板按此渲染）：

```
start → retrieval → citation* → answer → done
                 └─ refusal（低置信拒答，此时**不发** citation）
                 └─ error
```

每条帧带自增 `id`，前端断线重连时通过 `Last-Event-ID` 续发。

## 5. 关键设计决策（面试可讲）

### 5.1 为什么用 RRF 而不是加权求和

BM25 分数范围 `[0, +∞)`，向量相似度范围 `[-1, 1]`，**两者量纲不可比**。加权求和要么先归一化（对分数分布敏感、需反复调权重），要么直接相加（BM25 会完全压制向量分数）。RRF 只用排名 `1/(k+rank)`，天然免疫量纲问题且几乎免调参。

### 5.2 为什么"先切父块，再在父块内切子块"

"在全文上切子块，再用字符串位置反查归属父块"是**脆弱启发式**：文本可能重复出现、overlap 会让边界模糊，定位一错父子关系就错，回吐的上下文全是别的章节。改成嵌套切分后归属关系是**结构性确定**的。代价是父块边界限制子块跨度，但对章节式文档反而更好——子块永不跨章节。检索命中子块（精准），喂给模型的是父块（上下文完整）。

### 5.3 中文 BM25 的固有噪声与 `min_score`

中文走单字 + bigram 切分时，**任何中文查询几乎总能撞上几个高频单字**（"的"、"不"、"是"），这些字 IDF 很低但非零，会让无关文档拿到正分。实测噪声分 1.09，而相关查询在 6~8 量级。所以检索层加了分数下限过滤——它等价于一次"低置信拒答"，阈值按「拒答正确率 vs 漏答率」在评测集上扫出。

### 5.4 拒答判定必须用固定话术，不能只搜关键词

真实踩坑：用户问"精度要求是多少"，模型答"精度要求为 0.90"——若只搜 `未找到` 会误判。但换成搜**完整话术「知识库中未找到」并要求出现在回答前 60 字符内**，就既不会误伤正常回答，也能识别真拒答。

### 5.5 引用只在确定作答后才推送

初版 SSE 在生成答案**之前**就把 citation 推给前端了。结果是"拒答"场景下前端已经渲染了 3 条来源——用户看到"未找到"的回答配着引用，自相矛盾。正确顺序：检索 → 生成/判定 → （不拒答才发 citation）→ answer → done。

### 5.6 Reranker 的返回值契约

`rerank(query, pairs)` 的 `pairs` 是 `[(chunk_id, 正文)]`，返回值必须是 `[(chunk_id, score)]`。曾踩过的坑：返回正文当 id 也能"看起来正常工作"（排序是对的），但下游拿正文当 id 查文档必然返回空——引用溯源显示空片段、评测时 id 与 gold_ids 对不上，**而且不报错**。这类契约由单测守着。

## 6. 评测口径（★ 面试必答）

| 指标 | 正确口径 | 常见错误 |
|---|---|---|
| **MRR@K** | `1/rank`，**1-based**（第 3 位 = 1/3） | 用 0-based，MRR 虚高 |
| **Precision@K** | 分母**固定为 k** | 用"实际返回条数"当分母 |
| **Hit@K** | 前 K 条命中任一 gold 即 1 | 与 Recall 混用 |
| **幻觉率** | 忠实度**严格小于**阈值才计（`< 3`） | 用 `<=`，把边界算进去 |
| **召回 ≠ 准确** | 检索层报 Hit@5/MRR，生成层报忠实度/幻觉率，**分开报** | 混成一个"准确率" |

## 7. 已知局限与后续

- 当前评测集规模中等（119 条），**gold 标注需人工复核**（按关键词自动定位，存在循环论证风险）
- 尚未做多租户隔离与增量更新（新文档入库需重建索引）
- 未接入 RAGAs 等第三方评估框架（有意为之：自实现更可控且便于面试讲解）
- Dockerfile / docker-compose.yml 未在本机构建过镜像（配置一致性有单测守护）
